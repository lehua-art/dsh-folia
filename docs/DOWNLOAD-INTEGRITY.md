# 下载完整性保障（4.23.7）

> 为什么有这一页：4.23.6 修的是「下载完成了但装不上」，4.23.7 修的是更坏的一类 ——
> **下载"成功"了，但文件内容是坏的**。后者不会报错：job 报 `done`、长度和站点声明的一致、
> 面板上进度条也走完了，直到用户双击那个 zip 才发现打不开。

## 1. 事故现场（真实复现，不是构造）

站点对**同一个 URL** 有两个对象：

| 请求形态 | 返回的版本 | 长度 | ETag |
|---|---|---|---|
| 全量 GET（无 `Range`） | 旧版 | `17,509,106` | `"v1-…"` |
| `Range: bytes=a-b` | 新版 | `17,414,581` | `"v2-…"` |

旧的多连接实现（`lib/download-queue.js` 的 `fetchRanged`）把这 8 段**混着拼**进同一个
`.part`：

- 每段都只校验 `status === 206`；
- 每段的"实收字节"写的是 `return end - start + 1`（**请求长度**，不是收到的字节）；
- `base === 0` 时先 `truncateSync(part, total)` 把文件预填成 `total` 个 `0x00`。

于是：

```
落盘大小 = 17,509,106（和站点声明一致）
内容     = 旧版字节 + 新版字节 + 尾部 94,525 个 0x00
job      = done
```

`17,509,106 - 17,414,581 = 94,525` —— 尾巴上那截 0 就是"新版比旧版短的那一段"。

### 三行代码，三种"恒真"

| 位置（4.23.6 的 `lib/download-queue.js`） | 写法 | 后果 |
|---|---|---|
| `:387` | `return end - start + 1` | 收尾 `written !== span` **恒不成立**（永远等于请求总长） |
| `:369-373` | 只判 `r.status !== 206` | 双版本对象的字节被当成"同一份" |
| `:354-357` | `truncateSync(part, total)` | 收尾 `onDisk !== total` **恒不成立**（预填已把文件撑到 total） |
| `:378-385` | 无逐片计数 | 短读（body 少于请求）被静默吞掉 |

一句话：**长度判据被预填骗、总量判据被自己写死**，两个"校验"在这条路上从来没生效过。

## 2. 三层校验（现在的判据）

下载完成的定义从"文件长度对"扩成三道，**从传输到内容逐层收紧**：

### 第一层：长度（每片 + 收尾）

```js
let got = 0;                       // ① 逐片**实收**字节
src.on('data', (c) => { got += c.length; ... });
src.on('end', () => got !== want ? reject(new Error('range-short')) : resolve());
```

- 每片：`got === end - start + 1`，否则 `range-short:<got>/<want> @<start>-<end>`；
- 收尾：`Σ got === span`，再核 `statSync(part).size === total`。
- **不再预填** `0x00`：`base === 0` 只建空文件，写多少涨多少 ⇒ 落盘长度重新成为证据。
  （选择"按实际长度定长"而不是"维护已收区间"：区间在①已经逐片核对过、分片按构造连续覆盖
  `[base, total-1]`，再来一份区间账只是重复证据；而"文件长度"原本是唯一的独立证据，
  必须先让它恢复可信。）

### 第二层：`Content-Range` + `ETag`（是不是同一个对象）

```js
const cr = parseContentRange(r.headers.get('content-range'));
if (cr.start !== start || cr.end !== end) throw 'range-version-mismatch';
if (cr.total !== null && cr.total !== total) throw 'range-version-mismatch';
const etag = r.headers.get('etag');
if (etag && expectedEtag && etag !== expectedEtag) throw 'range-etag-mismatch';
```

- `start` / `end` 必须是**我们请求的那一段**；
- `/total` 必须是**全量响应给出的那个总量**（`*` 视为未知，不据此放行/拒绝）；
- 全量响应那次的 `ETag` 是"这一版对象"的见证人，各 206 的 `ETag` 若存在必须与它一致。

单流续传（`resumeSingle`）也吃同一条总量判据：从 `from` 续的 206 若报另一个 `/total`，
宁可明确失败，也不从那里往后写。

### 第三层：内容哈希（是不是那个文件）

站点清单里皮肤包 / 壁纸 / 开机动画 / 桌宠的条目带 `sha256`（**部分为空**）：

- 为空 ⇒ 这一层不设防（前两层仍然生效），绝不因为一条脏字段把下载判失败；
- 非空 ⇒ 落地前流式计算 `.part` 的 sha256，**不一致即判失败**。
  例：同一 URL 下站点重传了内容、CDN 回源到另一个构建、代理把 200 全量响应当 206 交付 ——
  前两层拦不住这些，只有哈希能答"这是不是那个文件"。
- 顺带修了"上次留下的坏文件"：HEAD 命中"大小 + ETag 一致"时，若清单给了 sha256
  **也会验一次已有文件**；对不上就当它不存在、照常重下（否则 4.23.6 之前拼坏的 zip 会永久留在本地）。

## 3. 失败回落路径（任何一步 throw 都不许停在中间态）

```
                        ┌──────────────── 单流下载（默认，auto 下 3 秒评估）
        fetchRanged ────┤
     （range-short /    │  任一 throw
      version-mismatch /│        │
      etag-mismatch /   └────────▼
      range-unsupported）  truncateSync(part, from)  ← 分片是并发按偏移写的，必须先截回切换点
                                    │
                                    ▼
                           resumeSingle(from)  单流续传（startAt=0 时清空重下）
                                    │
                      ┌─────────────┴─────────────┐
                  成功 │                           │ 失败 / 内容对不上
                      ▼                           ▼
                    done              failed(reason=...) —— 明确原因，可 retry
```

**hash-mismatch 是唯一一条"自动重下一次"的路径**（且只一次）：

1. 删掉 `.part` 与已落地的目标文件（坏文件一个字节都不留）；
2. `failed`，`error = "hash-mismatch"`；
3. 自动把 job 放回队列，置 `singleOnly`（**换单流**重取同一批字节 —— 重试的意义是换一条
   传输路径，而不是把同一组分片判据再跑一遍）；`job.hashRetry` 记账，只此一次；
4. 仍然不一致 ⇒ `failed`，`error = "hash-mismatch: 传输内容与站点不一致"`，不再自动重试
   （用户手动再点一次是**新的一轮**，仍可再享受一次自动重下）。

### 4.1 「旧实现会红」的证据（不是"我相信"）

⑥ 由三部分组成，缺一条都不算：

- **⑥a 源码级判据**：取出真 `fetchRanged` 的函数体，要求同时具备
  `got += buf.length` / `got !== want` / `range-short` / `content-range`（start、end、`/total`
  三项）/ `range-etag-mismatch` / "只建空文件"，且**不得**出现
  `return end - start + 1` 与 `truncateSync(part, total)`。
- **⑥b 变异**：把上面六处逐个"贴回旧写法"喂给**同一个判据函数**，每一处都必须被判红且
  指对位置（证明判据不是恒真）。
- **⑥c/⑥d/⑥e 行为级**：把 4.23.6 的旧算法原样内嵌成 `legacyFetchRanged()`，对**同一个**
  双版本假站点跑一遍：
  - 它**不抛错**（"成功"）；
  - 产物大小 = `17,509,106`（长度"对"）；
  - 产物尾部恰好 `94,525` 个 `0x00`，sha256 与正确内容不同；
  - 把本测试 ① 的断言（`done && sha256 === 正确哈希`）喂给这个产物 ⇒ **判红**。

也就是说：把 `lib/download-queue.js` 回滚到 4.23.6，这条回归测试会闪红 —— 这正是 P0 回归该有的样子。

## 5. 缓存管理面板（同一版的另一半）

`GET /folia/cache/usage` + `POST /folia/cache/clear { targets }`（`lib/routes/cache.js`）：
五层用量（媒体库 / 站点媒体 / 皮肤包 / 已装皮肤 / Electron）与**分目标**清理。安全边界：

- 请求体里**只有目标名**（白名单），路径一律由宿主自己按 `DSH_HOME` 与 `%APPDATA%\dsh-desktop`
  算出；`..`、绝对路径、盘符、UNC 都不是合法目标 ⇒ **整单 400**（一个坏名字就一个都不执行）；
- 算出的每个目录必须落在允许根之内（`isWithin`，用 `relative` 而不是字符串前缀）；
- **不跟随符号链接**：统计用 `lstat`、软链只计"跳过的链接"；清理只删链接本身；
- 删不掉（被占用）的文件进 `failed`、其余照删、响应 `partial:true`，**不 500**；
- `skins` 必须**显式点名**才清（清掉 = 皮肤中心的皮肤全部卸载），面板上是唯一一个两段式确认的按钮；
- 清完把 `downloads.json` 里**对应 kind 且 done** 的记录摘掉，避免"done 但文件已经没了"。

判据在 `test/verify-cache-manager.mjs`（**67 条**）：各 target 只删自己、诱饵目录一个字节不动、
路径穿越 400、符号链接不跟随、操作系统级"被占用"文件进 failed（Windows 用
`FileShare.None` 真占用，POSIX 用父目录去写位）、`skins` 只有点名才清、面板五个按钮各自
只发自己的 targets、两段式确认（第一下只上膛）、toast 报"释放 X"。

## 6. 本地副本自愈（4.23.15）

### 6.1 为什么还要有这一节

第 2 节的三层校验管的是**下载那一刻**。可它管不到两件事：

1. **历史遗留**：4.23.6 之前下的成品可能是"长度对、内容错"（ranged 静默损坏），
   而这些 job 的状态是 `done` —— 面板的"缓存命中 4/5"数的是 job，不是字节；
2. **本机解不了**：内容完全正确，但这台机器的解码器吃不消（5916×2530 / 10-bit / HEVC）。

真实故障：另一台机器壁纸报「视频解码失败（文件可能已损坏）」，而面板同时说"缓存命中 4/5"。
两句话都不假 —— **播放路径直接读本地文件，没有任何自检**，所以坏字节会永久留在 library 里，
用户每次点都是同一句错误，且没有任何自愈手段。

### 6.2 判据（`lib/media-verify.js`，分三档，越往下越贵）

| 档 | 判据 | 用在谁身上 | 结论 |
|---|---|---|---|
| ① size | 与 job 记下的总长度比 | 所有文件 | 不等 ⇒ `size`（截断/半截写） |
| ② sha256 | 与**站点清单**的 sha256 比（≤20 MB 全量流式算） | 已知 sha 且 ≤20 MB | 不等 ⇒ `sha`（"长度对、内容错"那一类） |
| ③ 结构 | MP4 顶层 box 走一遍：有没有 `moov`、有没有 box 越界 | 大文件 / 没有 sha 时 | ⇒ `struct` |

⚠️ **见到 `moov` 不能立刻收工**：moov 在文件头、mdat 却被截断，正是"能解复用、一播就崩"的
形态。所以 box 链一路走到尾，让"越界"这条判据有机会开口（早退会把截断判成完好 ——
本仓的第一次实现就是这么写的，`test/verify-media-selfheal.mjs` 的 D3/H5 把它抓了出来）。

⚠️ **有 sha256 就必须按 sha256 判**。只比长度会把"长度对、内容错"判成好文件，而后者恰恰是
4.23.6 事故的形态。负对照把 `decideHeal()` 里的 sha 分支从**真源码里摘掉**，断言同一条证据下
它给出别的结论（= 第一条用例会红）。

### 6.3 处置结论（`decideHeal()`，纯函数）

| 证据 | 结论 | 动作 | 文案 |
|---|---|---|---|
| sha 不符 / 结构坏 / 文件没了 | `corrupt` | 删成品 + `.etag` + `.part`、作废完成记录、**单流**重下 | 文件已损坏，已重新下载 |
| sha 相符、源是原画、有 1080p 变体 | `variant` | 入队 1080p；原画标 `decodeUnsupported`（后续 `localCopyFor()` 跳过它） | 已自动切换 1080p（原画超出本机解码上限） |
| 内容没问题、无变体、救援转码可用 | `transcoded` | ffmpeg 产出 H.264 / **yuv420p** / ≤1080p | 原画超出本机解码上限，已生成本机可播放的 1080p 副本 |
| 已在 1080p 仍失败 / 转码失败 | `undecodable` | 不重下、不再换档 | 本机不支持该编码（可换一张跳过此壁纸） |
| 内容没问题、无变体、转码不可用 | `undecodable-no-variant` | 同上 | 该壁纸分辨率/编码超出本机解码能力（可换一张跳过此壁纸） |

**不作弊成"播原片"**：转码失败或不可用时明说解不了 —— 静默回退会让用户以为已经修好，
然后撞上同一个错误。`/folia/local-media/<id>?playable=1` 在产物不存在时回 404，也是同一条纪律。

### 6.4 三条入口

1. **播放失败**（P0）：`<video>` 的 `MEDIA_ERR_DECODE`(3) / `SRC_NOT_SUPPORTED`(4) 且当前源是
   本地副本 ⇒ 客户端 `POST /folia/local-heal`。网络类错误(2)与中断类(1) **不走自愈** ——
   那是"这一下没传完"，重下只会把一份好文件换掉。每张壁纸最多自愈 2 次（防死循环）。
2. **启动自检**（采样）：挂载后 **30 s**（`unref`，不阻塞）对 library **最近 20 个**成品
   （按文件 mtime 倒序）逐条串行校验；坏的 ⇒ 后台删掉 + 排回下载队列，不弹窗。
   `DSH_FOLIA_SELFCHECK_DELAY_MS` 可调窗口（测试用）。
3. **全量校验**：面板「校验并修复本地媒体」⇒ `POST /folia/local-verify`，与采样**同一条代码路径**，
   只是范围从"最近 20"变成"全部 done"。完成后刷新清单（角标会跟着变）。

读数口径（`GET /folia/local-check`）：`damaged` = 累计发现；`cleaned` = 已删并排回队列；
`pending` = 还没修好的。面板那行「损坏文件：N 个（已清理 C / 待重下 P）」逐字取这三个数。

### 6.5 救援转码（没有变体时的最后一档）

`lib/media/transcode.js` 的 `transcodeToPlayable()`：`scale≤1920×1080` + `-pix_fmt yuv420p` +
**只接受 H.264**（`h264_nvenc` → `libx264`）。为什么不用 AV1：AV1 在旧 Chromium 上本来就是
"解不了"的一员，救援拿它当首选等于赌用户的浏览器够新。

缩放滤镜算的是**具体像素**（`playableScaleFilter()`）而不是 `scale=min(1920,iw):-2`：
`min()` 里的逗号在 filtergraph 里是分隔符，作为单个 argv 必须转义，漏一个反斜杠 ffmpeg 就会
把它解析成两个滤镜 —— 一个只在真机才看得见的坑。

缓存键 `abs|mtime|x1080-playable`（与抽帧键 `abs|mtime|fps` **不同前缀**，永不撞车）。
产物落盘后**再过一遍完整性判据**（`size>0` + `moov` + 不越界）：转码写一半的残片若被当成
"救回来的文件"，用户会看到同一个错误再来一次，而我们以为已经修好了。

### 6.6 判据在哪

`test/verify-media-selfheal.mjs`（**81 条**，`npm run verify` 硬档）：

- 假 HTTP 源 + 真下载队列 + 真自愈：篡改字节（**长度不变**）⇒ `corrupt` ⇒ 删 + **单流**重下
  ⇒ 最终字节与站点**逐字节一致**（= 这份文件能播）；
- 好文件 + 解码失败 ⇒ **不重下**（job 仍 done、字节没变、没有新 GET），切 1080p 变体；
- 无变体 ⇒ 转码被调用**恰好一次**；转码失败 ⇒ `undecodable`；已在 1080p ⇒ `undecodable`；
- 启动自检采样口径：25 个成品只取最近 20、最旧 5 个不参与；
- 1 个"长度对 sha 错" + 1 个截断 ⇒ 两个都被标记、都被清掉、都排回队列；
- 负对照三条（源码级）：摘掉 sha 校验只比长度 ⇒ 第一条用例红；只按速度选档 ⇒ 解码上限用例红；
  直接报错不降级 ⇒ 静态帧用例红。

### 6.7 「最终必须能上屏」的四级链（用户最终目标）

需求原文：**任何一张壁纸，只要站点上有可用文件，最终都必须能上屏**。所以处置不是二选一：

| 级 | 条件 | 动作 | 文案 |
|---|---|---|---|
| 1 | 站点有 1080p 变体 | 播变体 | 已自动切换 1080p（原画超出本机解码上限） |
| 2 | 无变体、转码管线可用 | 救援转码（≤1920×1080 / H.264 / yuv420p / +faststart） | 原画超出本机解码上限，已生成本机可播放的 1080p 副本 |
| 2′ | 转码中 | 每 1.5s 轮询 + 百分比/ETA | 正在生成本机可播放副本 {percent}%（约剩 {eta} 秒） |
| 3 | 转码失败/不可用 | 静态帧兜底（缩略图/首帧铺上屏） | 已降级为静态壁纸（本机不支持该视频解码） |
| 4 | 连静态帧都没有 | 才允许报错 | 无法显示这张壁纸（…且没有可用的静态帧） |

不变量：
- **不许静默**：转码期间必须有数字（percent 与抽帧那条 `/transcode-progress` 同一公式；
  eta 拿不到就只报百分比，不编）；上限报 99%。
- **静态帧兜底不拆 `<video>`、不重建层**：只在同层追加一个 `.we-media` 的 `<img>`。
  拆池元素会把 4.23.8 那本"谁在屏上"的账弄乱。
- **只有第 4 级才允许"无法显示"**：前三级任一成功都必须有画面。

### 6.8 顺带钉住的一个"以为是它、其实不是"的假设

用户怀疑"以前靠 60fps→30fps 降帧还能播，现在不行了"。代码证据（4.23.15 的树上）：

- `src/live-layer.js:503` 仍然调用 `videoChannelAfterLayerBuild(video, selection)`
  （`syncLayers` 是唯一编排点，池化只换了元素来源、没换编排）；
- `src/video-layer.js:611-613` 把它转给 `maybeUpgradeToTranscoded(...)`；
- 而 `maybeUpgradeToTranscoded` 第一句是 `if (!cap || cap <= 0) return`，`fpsCap` 默认 **0**
  （`lib/settings-schema.js`）⇒ **默认永不抽帧**。

所以降帧升级既没被绕过、也从来不是解码救援：它是"压解码占用"的可选功能。
超限源的兜底只能是 6.7 那条链（选档避开 → 变体 → 转码 → 静态帧）。
§10 一节把"注释掉调用 ⇒ 红"做成了负对照，将来谁把这条链接拆掉都会立刻变红。
