# 远程媒体（站点壁纸）性能设计 —— 别只让"我这台机器"变快

> 这份文档是**给所有装了我们插件的人**写的，不是给某一台机器写的。
> 起因：作者本机切一张站点壁纸要等数秒。第一版修法是"给站点视频补 poster"（已落地），
> 但那只是**遮住等待**；真要让人不再等，得把"远程 → 本地"这条路做对。
> 本文把"别人电脑上会遇到什么"逐条列出来，并给出与机器无关的判据。

---

## 0. 先分清两件事：**感知延迟** 与 **真实耗时**

| 指标 | 定义 | 由谁决定 |
|---|---|---|
| 感知延迟 | 点「应用」到**屏上有画面** | 我们的层闸门：有 poster/首帧就放行 |
| 真实耗时 | 到**视频真的在播** | 网络 + 文件大小 + 解码能力 |

第一版只改了感知延迟（站点静态缩略图当 poster，`src/video-layer.js` 的 `siteStaticThumb`）。
它有效、且**与机器无关**（任何有静态 thumb 的站点条目都受益），但它不减少流量、也不解决重复切换。

---

## 1. 为什么"别人电脑上"会不一样：六个差异面

| 差异面 | 我们这台 | 别人可能 | 我们的对策（与机器无关的判据） |
|---|---|---|---|
| **网络** | 家宽直连、低 RTT | 4G / 弱网 / 公司代理 / 高丢包 | ① 边下边播（不让用户等整包）② 支持 Range 续传 ③ 失败**降级到直连原 URL**，绝不因缓存层坏掉就看不了壁纸 |
| **代理** | 无 | `HTTP(S)_PROXY` 环境变量 / 系统代理 | 宿主 fetch 默认**不读**系统代理 ⇒ 必须显式支持 `HTTP_PROXY/HTTPS_PROXY/NO_PROXY`，否则这类用户整站都拉不到 |
| **站点可达性** | 站点在本机 200ms 内 | 站点被锁 / 跨境慢 / DNS 污染 | ① `site-locked` 明确提示（已做）② 清单**本地缓存**（离线也能看已装/已缓存）③ 超时后不阻塞其它页签 |
| **磁盘** | D 盘、空间充裕 | C 盘紧张 / 无写权限 / 网络盘 | ① 缓存目录走 `$DSH_HOME`，可用 `DSH_HOME` 覆盖 ② 写失败**静默降级为不缓存**（功能不受影响）③ 容量上限 + LRU，默认保守 |
| **CPU / 解码** | 独显、4K 能解 | 核显 / 老 CPU / 4K 卡顿 | 已有帧率上限与抽帧升级（本机媒体）；**远程缓存落地后**才能对它做同样的事（先缓存才能 ffmpeg） |
| **DSH 版本** | 0.2.1-rc.3 | rc.1 / rc.2 / 未来 0.3 | 引擎声明 `^0.2.0-rc.1`；皮肤中心的门槛单独降级（不影响壁纸） |

**结论**：远程媒体这条路必须做到"**缓存层是可选的加速器，不是必经路径**"。
它挂了、满了、没权限了，用户仍能直连原 URL 播放（只是慢一点）。

## 2. 目标设计：`/folia/site-media?u=<encoded>`（本机缓存代理）

### 2.1 请求流

```
<video src="/folia/site-media?u=https%3A%2F%2F<站点>/media/.../x.mp4">
        │
        ├─ 命中缓存（完整文件）：直接 serveFile（Range / HEAD / 206，复用 lib/serve.js）
        │      ⇒ 第二次起，切换 = 本地磁盘读（与"本机壁纸"同一条快路）
        │
        ├─ 未命中：向上游发起带 Range 的请求，**边转发边落盘**（.part → 完成后 rename）
        │      并发同一 URL 只发起一次上游请求（in-flight 去重），其余等同一份
        │
        └─ 上游失败 / 缓存目录不可写 / 超容量：**302 到原 URL**
                ⇒ 用户仍能看到壁纸，只是没有加速（缓存层永不是单点故障）
```

### 2.2 五条防线（缺一条就不能上线）

1. **只代理白名单源**：`u` 必须是 http(s)，且 **host === 站点基址的 host**、
   路径前缀在 `/media/` `/assets/` 之间。否则就是开放代理 / SSRF。
2. **容量上限 + LRU**：默认 `2 GB`（可配）；按 `atime` 淘汰；启动时扫描一次做账，
   运行中每落盘 N 次校对一次，避免"几万个小文件"式失控。
3. **可写性探测**：启动时试写一个哨兵文件；失败 ⇒ 整个缓存层标记 `disabled`，
   所有请求走 302 直连（这条让"无写权限/只读盘"的机器表现与正常机器一致，只是不加速）。
4. **中断恢复**：`.part` + `.part.json`（记录 `url / etag / size / downloaded`）；
   再次播放同一 URL 时用 Range 续传；`etag/last-modified` 变了就整份重下。
5. **超时与并发**：上游 connect/首字节超时（默认 8s）即放弃并 302 直连；
   全局并发上限（默认 2～3 条大文件流），避免弱网下自己把带宽打满。

### 2.3 键与命名

```
key = sha256(url) 的前 32 hex + 原扩展名（.mp4/.webm/.jpg…）
目录：$DSH_HOME/cache/site-media/<key>         （完成）
      $DSH_HOME/cache/site-media/<key>.part    （在途）
```

用 `sha256(url)` 而不是 slug：站点重传文件会换 URL（`…/715028863ae3.zip` 带内容哈希），
**换 URL 即换键**，天然不会拿到旧内容；同 URL 才算同一份缓存。

## 3. 客户端只需要改一处

站点条目（`source === 'folia'` 且 URL 是 http(s)）的 `media` 改成走代理：

```js
src = '/folia/site-media?u=' + encodeURIComponent(item.media)
```

**它必须同时保留"直连"这条腿**：代理返回 302 时浏览器会自己跟到原 URL，
所以 `<video>` 不需要任何额外逻辑；这一点是设计的核心，不是巧合。

## 4. 判据（守住"别人也能用"，不只守我一台）

| 判据 | 为什么是它 |
|---|---|
| **302 降级**：缓存不可写 / 上游 404 / 401 时返回 302 到原 URL | 缓存层坏了不能让人看不到壁纸（跨机器最关键的一条） |
| **白名单**：非站点 host 一律 400 | 否则插件会变成开放代理（安全面） |
| **容量与 LRU**：写入超过上限后旧条目被淘汰，总量仍 ≤ 上限 | 别人的 C 盘可能只有几 G |
| **续传**：`.part` 存在时用 Range 续，不从头下 | 弱网/断网是常态 |
| **去重**：同一 URL 并发只发起一次上游 | 轮播/预取会重复请求同一张 |
| **可写失败=不加速**：只读盘上功能与正常机器等价 | 只读/网络盘用户不该看到报错 |
| **离线清单**：站点不可达时仍显示已装/已缓存 | 站点是别人的服务，可能挂 |

每条都要有**负对照**（把这一条改坏 ⇒ 判据变红），与仓库既有守卫风格一致。

## 5. 分阶段（每阶段可独立上线）

| 阶段 | 内容 | 用户能感知到的变化 |
|---|---|---|
| ✅ 已做 | 站点静态缩略图当 poster | 切站点壁纸**立刻**有画面（不再黑场等首帧） |
| 待做 A | 缓存代理 + 302 降级 + 上限/LRU + 续传 | **重复**切换同几张：秒开；弱网：边下边播 |
| 待做 B | 预连接/预取首字节（清单加载时 `preconnect`） | 每次省 100～300ms |
| 待做 C | 远程文件落地后再做帧率抽帧（复用现有转码） | 核显/老 CPU 上 4K 不再卡 |
| 待做 D | 离线清单缓存 | 站点挂了仍能看已装与已缓存 |

---

## 6. 明确不做（以及为什么）

- **不做"整包预下载"**：把 29 MB 先下完再播，等于把等待放大到最坏情况。
- **不引入第三方缓存库**：本仓的发布面要求零额外运行时依赖（`dependencies` 只有
  `webwallgl`/`x11` + 随身携带的皮肤中心）；缓存逻辑 ~200 行，自己写更可控。
- **不把缓存目录放到 `%TEMP%`**：会被系统清理，导致"昨天快今天慢"的随机体验；
  放 `$DSH_HOME/cache` 并与已有 `cache-prune` 共用淘汰口径。
